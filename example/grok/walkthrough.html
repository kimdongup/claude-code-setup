Grok Build 세트 실전 가이드 — 할 일 앱 만들기

`template/grok/` 의 설정을 Grok Build 규약으로 실제로 굴려 보는 6단계 기록입니다. 각 단계의 터미널 화면은 example/grok/run-demo.sh 를 실행해 실제로 만들어졌습니다.

6 단계 스킬 86 에이전트 9 명령 6 훅 4 녹화 6/6

단계

  1. 01빈 폴더에서 시작하기 + 로드 확인
  2. 02프로젝트 기억 만들기
  3. 03TDD로 도메인 만들기
  4. 04하네스 규약이 다르면 훅이 죽는다
  5. 05서브에이전트로 리뷰시키기
  6. 06명령으로 돌리고 CI로 지킨다

STEP 01 빈 폴더에서 시작하기 + 로드 확인

목표 — 빈 저장소 + Grok 템플릿 적용 + grok inspect 로 실제 인식 확인

Claude Code 에 입력한 프롬프트

빈 폴더에 Node.js 할 일 앱을 새로 만들자. 먼저 git 저장소를 초기화하고 feature 브랜치에서 시작해줘. main에서 직접 편집하지 않는 규칙을 지키고 싶어.

  • `.claude/settings.json` — `UserPromptSubmit` · `PreToolUse` · `PostToolUse` 훅 3종이 정의돼 있다. 앱을 시작하는 시점에 이 파일이 함께 들어온다.
  • `.grok/agents/` · `skills/` — 역할 9개와 지식 86개가 붙는다. `grok inspect` 로 실제로 읽혔는지 눈으로 확인한다.
  • `AGENTS.md` — 세션마다 읽히는 기억 파일. `CLAUDE.md` 로 바꿔도 Grok 가 읽고, 다른 도구까지 고려하면 이 이름이 표준이다.
이 단계에서 배울 것`.grok/` 로 설치하면 `grok inspect` 에 바로 보인다. **그래도 `--trust` 를 먼저 써야 한다** — 신뢰 전에는 0 개로 보인다.

STEP 02 프로젝트 기억 만들기

목표 — 프로젝트 규칙을 CLAUDE.md 에 기록

Claude Code 에 입력한 프롬프트

이 프로젝트는 의존성 없이 Node.js 내장 테스트 러너(node:test)만 쓴다. … 이 규칙을 CLAUDE.md에 기록해줘.

  • `CLAUDE.md` — 스택·금지 사항·자주 쓰는 명령까지 적어두면, 매 세션마다 반복 프롬프트를 안 해도 같은 규칙이 적용된다.
  • `skills/*/SKILL.md` — 메모리가 '이 프로젝트 규칙'이라면 스킬은 '잘하는 방법'이다. 둘은 목적이 다르니 나눠 쓴다.
  • `agents/*.md` — 메모리가 규칙이면 에이전트는 역할이다. `description`에 언제 쓸지 써야 Claude가 자동으로 고른다.
이 단계에서 배울 것좋은 CLAUDE.md 는 **부재**를 적는다. '하지 말 것'을 명시해야 안 하는 일이 안 일어난다.

STEP 03 TDD로 도메인 만들기

목표 — 테스트가 깨지는 것부터 시작해 도메인 구현

Claude Code 에 입력한 프롬프트

testing-patterns 스킬을 적용해서 할 일 도메인을 만들어줘. 빨강 상태로 시작하고, 한 번에 하나씩 테스트를 추가해.

  • `skills/testing-patterns/SKILL.md` — '프로덕션 코드 전에 실패하는 테스트를 먼저 쓴다'를 강제하는 스킬. 실제로 빨강→초록→리팩터 3회를 반복했다.
  • `testing-patterns` 규칙 — 테스트 이름은 `test('<조건> → <기대>')`. 세기가 Arrange/Act/Assert 세 블록으로 갈린다.
이 단계에서 배울 것테스트가 통과하기 **전**에 보인 실패가 있다는 게 이 단계의 증거다. 스크립트가 실제로 실행되어 녹화되어 있다.

STEP 04 하네스 규약이 다르면 훅이 죽는다

목표 — 설정의 훅을 실제 실행해 검증하고 프로젝트에 맞게 수정

Claude Code 에 입력한 프롬프트

Claude Code 전용으로 만들어진 훅이 Grok 에서도 그대로 동작하는지 확인해줘. stdin 으로 파일 경로를 받는 방식이면 그대로 가야 한다.

  • 도구 입력 — `$CLAUDE_TOOL_INPUT_FILE_PATH` 환경변수 vs **stdin JSON** 의 `toolInput.file_path`. 전자만 있으면 조건문이 false 가 되어 훅이 아무것도 안 한다.
  • `.grok/hooks/hook-lib.sh` — `tool_input` 한 함수가 그 차이를 흡수한다. 같은 훅이 두 하네스에서 같은 결과를 낸다.
  • 차단 프로토콜 — Claude 는 stderr `{"block":true}`, Grok 는 stdout `{"decision":"deny"}`. `deny()` 가 둘 다 출력한다.
  • 신뢰(trust) — `grok inspect` 는 신뢰 전이면 전부 0 으로 보인다. 에러가 없으므로 파서 문제로 오해하기 쉽다.
이 단계에서 배울 것**조용히 죽는 훅**이 이 세트에서 고친 제1의 문제다. Claude 전용 훅을 그대로 옮기면 종료 코드 0 으로 아무 일도 하지 않는다.

STEP 05 서브에이전트로 리뷰시키기

목표 — code-reviewer 와 security-reviewer 로 지적을 받고 반영

Claude Code 에 입력한 프롬프트

@code-reviewer 방금 만든 src/ 를 리뷰해줘. @security-reviewer 새로 추가한 persist.js 도 봐줘. 외부 입력이 파일 시스템에 닿는 부분이 있나?

  • `agents/code-reviewer.md` — `let seq = 0` 이 모듈 최상위다. 저장소 인스턴스가 id 를 공유해서 테스트가 실행 순서에 의존하게 된다 — 지적 1.
  • `agents/code-reviewer.md` — `createStore(initial)` 이 받은 항목에 `id` 가 없다. 두 항목을 넣으면 둘 다 `id === undefined` 여서 `complete()` 이 둘을 동시에 건드린다 — 지적 2.
  • `agents/security-reviewer.md` — `persist.js` 의 `writeFile(filePath)` 에 경로 검증이 없다. `../../.ssh/authorized_keys` 로 어디든 쓸 수 있다.
  • `description` 필드가 라우팅 — 에이전트가 자동 선택되는 기준은 이름이 아니라 `description` 문장이다. '~할 때 사용' 형식이 실전에서 잘 통한다.
이 단계에서 배울 것두 에이전트 다 **재현 가능한 판정**으로 바꿔 담았다. 같은 파일에 다시 돌리면 같은 결과가 나온다.

STEP 06 명령으로 돌리고 CI로 지킨다

목표 — /code-quality 로 게이트를 만들고 CI로 고정

Claude Code 에 입력한 프롬프트

/code-quality src 그리고 이 결과가 CI에서 막히게 만들어줘.

  • `commands/code-quality.md` — `$ARGUMENTS` 로 대상 디렉터리를 받는 슬래시 명령. 검사 목록이 이미 문서화돼 있다.
  • `.github/workflows/ci.yml` — PR이 올라오면 테스트→리뷰→보안→의존성 감사가 자동으로 돌고, 하나라도 실패하면 병합이 막힌다.
  • `includeCoAuthoredBy` — `settings.json` 의 값이 그대로 커밋 trailer에 반영된다.
이 단계에서 배울 것로컬에서 '기록만 남는 대시보드'와 CI에서 '병합을 막는 게이트'는 다르다. 6단계는 그 차이를 만든다.
